## 冲突解决详情

### 1. hermes_cli/main.py（3 处冲突）

**冲突原因：**
我们在多处 `subprocess.run` 调用（`systemctl is-active`、`systemctl show ... RestartUSec`、`systemctl show ... MainPID`）中添加了 `encoding="utf-8", errors="replace"`（Windows UTF-8 编码修复）。上游仅有 `capture_output=True, text=True, timeout=5`。

**解决方案：**
全部采用 HEAD 版本，保留 UTF-8 编码修复：

```python
result = subprocess.run(
    scope_cmd_ + ["is-active", svc_name_],
    capture_output=True, text=True,
    encoding="utf-8", errors="replace", timeout=5,
)
```

注：这些 systemctl 调用在 Linux 上无影响（默认 UTF-8），但保留编码参数可避免在跨平台测试或 WSL 环境下的回归。

---

### 2. hermes_cli/profiles.py（1 处冲突）

**冲突原因：**
上游将 `subprocess.run(["which", name], ...)` 改为 `subprocess.run(["which", canon], ...)`（修复变量名一致性）。我们的版本仍使用 `name` 但添加了 UTF-8 编码参数。

**解决方案：**
两者均接受——使用上游的 `canon` 同时保留 UTF-8 编码参数：

```python
result = subprocess.run(
    ["which", canon], capture_output=True, text=True,
    encoding="utf-8", errors="replace", timeout=5,
)
```

### 3. hermes_cli/pty_bridge.py（1 处冲突）

**冲突原因：**
我们在 04-26 添加了 Windows ConPTY 后端（`_PTY_BACKEND == "win"` 分支调用 `_WinPtyProcess.spawn`，传 `backend="win"` / `backend="posix"` 给 `cls.__init__`）。上游新增了 `TERM` 环境变量回退（CI 环境无 `TERM` 时默认 `xterm-256color`），并将 `spawn_env = (os.environ.copy() if env is None else env.copy())` 改为本地副本。

**解决方案：**
合并双方逻辑——TERM 默认值适配在双后端分支前生效，Windows / POSIX 分支均使用同一份 `spawn_env`：

```python
spawn_env = (os.environ.copy() if env is None else env.copy())
if not spawn_env.get("TERM"):
    spawn_env["TERM"] = "xterm-256color"

if _PTY_BACKEND == "win":
    proc = _WinPtyProcess.spawn(
        list(argv), cwd=cwd, env=spawn_env, dimensions=(rows, cols),
    )
    return cls(proc, backend="win")
else:
    proc = ptyprocess.PtyProcess.spawn(  # type: ignore[union-attr]
        list(argv), cwd=cwd, env=spawn_env, dimensions=(rows, cols),
    )
    return cls(proc, backend="posix")
```

### 4. tools/environments/local.py（1 处冲突）

**冲突原因：**
我们在 04-24 添加了 Windows MSYS → Windows 路径转换（`_IS_WINDOWS` 分支调用 `msys_path_to_windows(self.cwd)` 生成 `popen_cwd`）。上游引入了 cwd 失效自动恢复机制（`_resolve_safe_cwd(self.cwd)`，回退到最近存在的祖先目录，issue #17558）——但 `os.path.isdir` 在 Windows 上无法解析 MSYS 形式的路径（`/d/...`），直接调用 `_resolve_safe_cwd(self.cwd)` 会误判为不存在并跳到 tempdir，破坏 Windows 终端命令。

**解决方案：**
调整顺序——先把 `self.cwd` 转换成 Windows 形式得到 `popen_cwd`，再用 `popen_cwd` 做存在性检查；恢复后同步把 `self.cwd` 写回 MSYS 形式以保持一致：

```python
if _IS_WINDOWS:
    from tools.platform_compat import msys_path_to_windows, windows_path_to_msys
    popen_cwd = msys_path_to_windows(self.cwd)
else:
    popen_cwd = self.cwd

safe_popen_cwd = _resolve_safe_cwd(popen_cwd)
if safe_popen_cwd != popen_cwd:
    logger.warning(
        "LocalEnvironment cwd %r is missing on disk; "
        "falling back to %r so terminal commands keep working.",
        self.cwd, safe_popen_cwd,
    )
    popen_cwd = safe_popen_cwd
    self.cwd = (
        windows_path_to_msys(safe_popen_cwd) if _IS_WINDOWS else safe_popen_cwd
    )
```

这样 cwd 失效恢复在 Windows 上也能正确触发，而 Windows 路径转换补丁完整保留。

### 5. ui-tui/package-lock.json（2 处冲突）

**冲突原因：**
本地 `npm install` 把若干依赖的 `resolved` 字段从 `registry.npmjs.org` 替换为 `registry.npmmirror.com`（npm 镜像源）。上游 lock 文件继续使用官方源。

**解决方案：**
采用上游版本（`git checkout --theirs`）。`integrity` 哈希一致，artifact 完全相同；走官方源更利于跨开发者协作，本地需要镜像加速时由 `~/.npmrc` 自行配置即可。
